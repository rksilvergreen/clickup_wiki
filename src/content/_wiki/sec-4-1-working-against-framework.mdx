<p>As discussed in <Link to="sec-3-5">ClickUp's Inadequacy</Link>, ClickUp’s core data model forces every entry into a task-shaped mold: assignees, due dates, priorities, and statuses are baked into the base schema regardless of whether the entry represents a work item, a record, an event, or something else entirely. ClickUp is aware of this rigidity and offers custom task types as an apparent remedy—but even with task types in place, none of the core task features can actually be removed. Task types do not introduce genuinely distinct schemas; they are simply a classification naming layer layered on top of the same underlying structure.</p>
<p>The result is that any attempt to impose a meaningful type scope hierarchy—where different kinds of entries carry different schemas, behaviors, and lifecycle rules—must be built against the grain of the platform rather than with it. ClickUp does not natively support scoping fields, automations, or status groups to task types; it only scopes them to locations in the project hierarchy. This means that the entire type-based structure documented in <Link to="sec-4-2">Type Scope Hierarchy</Link> exists as a set of deliberate conventions, workarounds, and compensating configurations rather than as something the platform enforces on its own.</p>
<p>This friction surfaces repeatedly across the workspace design:</p>
<ul>
  <li>Status groups in ClickUp are inherited through the project scope hierarchy—Spaces pass their status group to Folders, which pass it to Lists. Since we treat status groups as belonging to task types rather than locations, we must actively negate this inheritance. Every Space and Folder is assigned the <StatusGroupLink to="sec-4-4-1-4">Statusless</StatusGroupLink> status group, and meaningful status groups are applied only at the List level (see <Link to="sec-4-4-1-3">Status Group Assignment</Link>).</li>
  <li><Link to="sec-4-4-2">Tags</Link> are scoped only at the Space level: every list in a Space shares one tag namespace, with no way to tie a tag vocabulary to a single task type or list. That is too coarse for clean type-scoped semantics—we would want different buckets of meaning for different kinds of entries without cross-contamination. We work around it by using Tags only on <TaskTypeLink to="sec-4-2-1">Task</TaskTypeLink> (see <Link to="sec-4-4-2-1">Tag Assignment</Link>).</li>
  <li>Automations cannot be scoped to a task type. In a platform that genuinely supported a type scope hierarchy, an automation could be defined once against a type and apply wherever entries of that type appear. Instead, we maintain a centralized <Link to="sec-4-3-1-1-2">Automation Folder</Link> with a dedicated list per task type, and every entry is automatically added to its type’s list so that workspace-wide automations can be defined in a single place rather than duplicated across every individual project list.</li>
</ul>
<p>These are not edge cases. They are direct consequences of trying to build a type-driven structure inside a platform whose architecture only recognizes project-location-based scoping. Each workaround exists because ClickUp claims to support the kind of flexibility that a type hierarchy requires, yet does not follow through with the structural depth to make it work natively.</p>
