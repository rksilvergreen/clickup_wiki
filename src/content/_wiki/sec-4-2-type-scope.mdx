<p>The Type Scope hierarchy is built on the idea that the <BaseFieldLink to="task-type">Task Type</BaseFieldLink> field functions as a scope selector field. In ClickUp, this is not a formally recognized scope mechanism in the same way that location is for the project scope, but in our workspace we deliberately treat it as one. That is, we recognize that type meaningfully determines applicability, behavior, and structure, and we organize the workspace accordingly even if ClickUp itself does not systematically model task type as a true scope hierarchy.</p>
<p>This means that task type is not just a label for classification. It acts as a contextual boundary that helps determine what belongs to an entry and what does not. We create fields, status groups, tags, templates, automations, views, and filters that are intended for a specific task type and should not be used across others indiscriminately. The Type Scope section therefore describes the type-based structure we impose on the workspace: a conceptual scope hierarchy that we enforce through design, convention, and configuration rather than through a native ClickUp scoping system.</p>
<Section id="sec-4-2-1" title="Task">
<p>The default actionable work-item entry type, representing a unit of work that you intend to do, track to
  completion, and manage through a workflow. A Task has an owner (or owners), a lifecycle state, and often a due
  horizon; you can plan, prioritize, and advance it while keeping context in description, comments, attachments,
  and relationships. As the most operational type—meant for execution rather than just capture—it relies on
  ClickUp's built-in workflow machinery such as Status, Assignees, and Priority.</p>

<Section id="sec-4-2-1-1-1" title="Max Start Date">
<p>The <TaskTypeFieldLink type="task" to="max-start-date">=Max Start Date</TaskTypeFieldLink> field computes the latest possible date from which work on the task can begin and still be completed by its <TaskTypeFieldLink type="task" to="due-date">Due Date</TaskTypeFieldLink>. It derives the number of days required by dividing the task's <TaskTypeFieldLink type="task" to="sprint-points">Sprint Points</TaskTypeFieldLink> by a daily throughput rate and rounding up, then subtracts that number of days from the Due Date to produce a deadline-driven latest start. If the task's <TaskTypeFieldLink type="task" to="start-date">Start Date</TaskTypeFieldLink> is already later than this computed date—meaning the window for on-time completion has passed by the time the task becomes available—the field returns the Start Date instead, since work cannot begin before it regardless. When Sprint Points is zero, minimal effort is required and the field simply equals the Due Date.</p>
<p>In effect, =Max Start Date always yields the later of the task's Start Date and the computed deadline-driven latest start, giving a single date that answers: "What is the absolute latest I can begin this task and still finish on time?"</p>
</Section>
<Section id="sec-4-2-1-1-2" title="Task Derived Properties">
<p>Several derived properties of a task—not stored as fields themselves, but computed from combinations of the fields above and from the task's place in the workspace—are referenced throughout this wiki. The following terms name those properties:</p>
<ul>
  <LinkTarget as="li" id="task-term-specified"><strong>Specified</strong> — A task is <em>specified</em> when all of the following are set: its <TaskTypeFieldLink type="task" to="assignees">Assignees</TaskTypeFieldLink>, its <TaskTypeFieldLink type="task" to="priority">Priority</TaskTypeFieldLink>, and at least one of <TaskTypeFieldLink type="task" to="sprint-points">Sprint Points</TaskTypeFieldLink> or <TaskTypeFieldLink type="task" to="time-estimate">Time Estimate</TaskTypeFieldLink>. If any of these is missing, the task is not specified.</LinkTarget>
  <LinkTarget as="li" id="task-term-blocked"><strong>Blocked</strong> — A task is <em>blocked</em> if any of the following holds: (1) its <TaskTypeFieldLink type="task" to="dependencies">Dependencies</TaskTypeFieldLink> include a "blocked by" relationship to another entry; (2) its <TaskTypeFieldLink type="task" to="status">Status</TaskTypeFieldLink> is <StatusLink type="task" status="blocked" />; or (3) its <TaskTypeFieldLink type="task" to="status">Status</TaskTypeFieldLink> is <StatusLink type="task" status="waiting" />.</LinkTarget>
  <LinkTarget as="li" id="task-term-sprinted"><strong>Sprinted</strong> — A task is <em>sprinted</em> when it belongs to an <Link to="sprint-term-open">open sprint</Link> inside the sprint folder.</LinkTarget>
  <LinkTarget as="li" id="task-term-sprint-relevant"><strong>Sprint relevant</strong> — A task is <em>sprint relevant</em> for a given sprint if its <TaskTypeFieldLink type="task" to="start-date">Start Date</TaskTypeFieldLink> is the sprint's last day or earlier, or the <TaskTypeFieldLink type="task" to="start-date">Start Date</TaskTypeFieldLink> is not set.</LinkTarget>
</ul>

<Section id="sec-4-2-1-3" title="Task Tags">
<p>Tags are meant to express the <em>character</em> of a task: what doing it is like in practice—where your body and attention need to be, what kind of friction or facilitation it involves, and what “mode” the work lives in. They are not a substitute for status, estimates, or labels; they answer a different question, namely “what sort of thing is this, experientially and logistically?” Use them when a glance at the task name should carry that texture forward into planning and triage (for example, knowing that something is outward-facing, physically anchored, or dependent on a contact changes how you batch it, when you attempt it, and what you prepare beforehand).</p>
<p>The tags defined for this workspace are:</p>
<ul class="doc-tag-list">
  <li><Tag color="#b1b1b1">bureaucracy</Tag> — Administrative or procedural work: forms, paperwork, official processes.</li>
  <li><Tag color="#a875ff">contact required</Tag> — Requires reaching out to someone outside the household—a service rep, friend, or family member.</li>
  <li><Tag color="#b7c059">digital</Tag> — Can be done entirely on a device (computer, phone, tablet).</li>
  <li><Tag color="#63beb4">household</Tag> — Physical work or chores in and around the home.</li>
  <li><Tag color="#3e63dd">maintenance</Tag> — Keeping something in working order—upkeep, repairs, routine care.</li>
  <li><Tag color="#248f7d">medical</Tag> — Relates to health: appointments, treatments, or medical administration.</li>
  <li><Tag color="#0091ff">outside</Tag> — Must be done away from home; requires going out.</li>
  <li><Tag color="#ab4aba">recreation</Tag> — Leisure, hobby, or entertainment—something enjoyable rather than obligatory.</li>
  <li><Tag color="#6e56cf">self-care</Tag> — Personal well-being: rest, reflection, or looking after oneself.</li>
  <li><Tag color="#96f1fb">social</Tag> — Involves spending time or interacting with others outside the household.</li>
</ul>
</Section>

<Section id="sec-4-2-2" title="Event">
<p>An Event represents something that happens at a defined period in time—it has a start and an end, and it is
  about when it occurs and when the user should be made aware of it in advance. Events let you record and track

  display. The workspace derives precise =&Start Time and =&End Time from the dates you set, derives <TaskTypeFieldLink type="event" to="status">Status</TaskTypeFieldLink> from
  those times, and computes an <TaskTypeFieldLink type="event" to="relevance-date">=&Relevance Date</TaskTypeFieldLink> so the event can be shown or notified ahead of

<Section id="sec-4-2-2-1-1" title="Event Time Derivation">
<p>ClickUp's <TaskTypeFieldLink type="event" to="start-date">Start Date</TaskTypeFieldLink> and <TaskTypeFieldLink type="event" to="due-date">Due Date</TaskTypeFieldLink> default to 4:00 AM on the given day when
  the user does not specify a time—the system treats this 4:00 AM Jerusalem time as "no time set." That default
  is unsuitable for events, so <TaskTypeFieldLink type="event" to="start-time">=&Start Time</TaskTypeFieldLink> and <TaskTypeFieldLink type="event" to="end-time">=&End Time</TaskTypeFieldLink> exist as auxiliary
  computational fields: the system populates them from <TaskTypeFieldLink type="event" to="start-date">Start Date</TaskTypeFieldLink> and <TaskTypeFieldLink type="event" to="due-date">Due Date</TaskTypeFieldLink>
  using the rules below, treating any time other than the 4:00 AM default as a real time and using it as-is. The
  user works only with <TaskTypeFieldLink type="event" to="start-date">Start Date</TaskTypeFieldLink> and <TaskTypeFieldLink type="event" to="due-date">Due Date</TaskTypeFieldLink>; <TaskTypeFieldLink type="event" to="start-time">=&Start Time</TaskTypeFieldLink> and
  <TaskTypeFieldLink type="event" to="end-time">=&End Time</TaskTypeFieldLink> are not meant to be edited directly.</p>

<Section id="sec-4-2-4" title="Thought">
<p>A Thought is a <TaskTypeLink to="sec-4-2-3">Record</TaskTypeLink> that captures a thought—something that crossed your mind and that you want to keep. It might be a realization, an idea, a reminder to do something later, a placeholder for a task you haven't defined yet, a quote or insight worth revisiting, or a half-formed notion you're not ready to turn into anything else. There is no workflow; you get a timestamp and the content, with optional assignees like any <TaskTypeLink to="sec-4-2-3">Record</TaskTypeLink>. Structurally it is the same as <TaskTypeLink to="sec-4-2-3">Record</TaskTypeLink>.</p>

<Section id="sec-4-2-5" title="Milestone">
<p>A Milestone represents a meaningful date in a project timeline: a point that carries enough importance to stand out as a marker of progress, commitment, completion, approval, transition, or readiness. It is a date with significance—one that helps define where the project is, what has been accomplished, what must happen next, or what moment the work is building toward. A milestone can therefore capture things like a launch moment, a key decision point, a delivery commitment, a phase boundary, or any other notable checkpoint whose value lies in its importance to the project as a whole. It is a temporal anchor that gives structure and meaning to the broader flow of the project.</p>
<Section id="sec-4-2-5-1" title="Milestone vs Event">
<p>An <TaskTypeLink to="sec-4-2-2">Event</TaskTypeLink> is a date that holds an <em>occurrence</em>. It exists in the system because something happens at that time and the user needs to be aware of it when it arrives — whether that means attending it, preparing for it, observing it, or simply registering that it has come. An event typically, but not necessarily, spans a period of time, with a start and an end, since occurrences generally unfold rather than appear instantaneously; the occurrence itself can be anything from an active engagement to a passive happening.</p>
<p>A Milestone, by contrast, is a date that holds <em>significance</em>. Nothing necessarily "takes place" at a milestone in the way something takes place at an event; instead, the date itself is what matters. It marks a transition, a commitment, a completion, or a checkpoint within some larger trajectory — a project, a journey, a body of work, or any progression that gives the date its meaning. Because a milestone is a marker rather than an unfolding occurrence, it is a single point in time — one datetime, not a span. The date is not tied to an occurrence; it <em>is</em> the meaning.</p>
</Section>

<Section id="sec-4-2-6" title="Data">
<p>A Data type represents arbitrary information that is worth storing in the workspace. It is meant for content that may take many different forms and does not need to fit a fixed schema; its sole purpose is to preserve information.</p>

<Section id="sec-4-2-7" title="Parent Task">
<p>A Parent Task is a practical workaround used for <Link to="sec-4-2-1">Tasks</Link> that contain subtasks. When deciding what to do and what matters most, the real attention usually belongs on the subtasks, since they are the concrete items that need to be completed. The parent item still has value as the container that groups them under a larger objective, but showing it alongside its subtasks often adds clutter rather than clarity. Assigning it the Parent Task type makes it easier to filter out in views where the focus should remain on the lower-level actionable items, while still preserving the broader structure they belong to.</p>
