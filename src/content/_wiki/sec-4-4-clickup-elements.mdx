<Section id="sec-4-4-1" title="Statuses">
<p>A <strong>status group</strong> is the named collection of custom <BaseFieldLink to="status">Status</BaseFieldLink> values configured for a location (list, folder, or space), representing the lifecycle template for entries there. In ClickUp it is stored as part of the location&rsquo;s settings, not as a first-class object tied to task type—so while a status group often lines up with a single task type, that link is conventional in our workspace, not enforced by the product. Here, every list is strongly coupled with a task type, so the status group chosen for a list usually functions as that type&rsquo;s workflow track.</p>
<Section id="sec-4-4-1-1" title="Status Types">
<p>ClickUp classifies every custom status into one of four built-in <strong>status types</strong>—<StatusType group="Not started" />, <StatusType group="Active" />, <StatusType group="Done" />, and <StatusType group="Closed" />—which drive board columns, progress behavior, and related mechanics (see ClickUp&rsquo;s <a href="https://help.clickup.com/hc/en-us/articles/6309452618647-Manage-task-statuses" target="_blank" rel="noopener noreferrer">Manage task statuses</a>). That requirement applies even when an entry is not really a &ldquo;task&rdquo; in everyday language; we map each status to the most sensible type we can.</p>
<ul>
  <LinkTarget as="li" id="cu-status-type-not-started"><StatusType group="Not started" link={false} /> — For work that has not yet begun; items here are queued or unpulled relative to active effort.</LinkTarget>
  <LinkTarget as="li" id="cu-status-type-active"><StatusType group="Active" link={false} /> — For work in motion: in progress, waiting on something, or otherwise live before a terminal outcome.</LinkTarget>
  <LinkTarget as="li" id="cu-status-type-done"><StatusType group="Done" link={false} /> — For successful completion: the intended outcome was reached (ClickUp&rsquo;s successful closed column).</LinkTarget>
  <LinkTarget as="li" id="cu-status-type-closed"><StatusType group="Closed" link={false} /> — For terminal states that are not successfully completed in that sense—canceled, voided, or otherwise finished without that meaning (ClickUp&rsquo;s unsuccessful closed column).</LinkTarget>
</ul>
</Section>
<Section id="sec-4-4-1-2" title="Status Transitions and Triggers">
<p>A status change is a transition: moving an entry from one lifecycle state to another. In our
  workspace, transitions can be driven by four kinds of triggers:</p>
<ul>
  <LinkTarget as="li" id="status-trigger-manual"><StatusTrigger>Manual</StatusTrigger> — The user explicitly changes the status based on judgment calls and intangible factors that the workspace can't reliably capture or analyze.</LinkTarget>
  <LinkTarget as="li" id="status-trigger-internal-conditional"><StatusTrigger>Internal Conditional</StatusTrigger> — Some change in the entry or elsewhere in the workspace triggers the transition.</LinkTarget>
  <LinkTarget as="li" id="status-trigger-external-conditional"><StatusTrigger>External Conditional</StatusTrigger> — A real-world event outside the workspace happens, but it's still something that can be pinpointed and articulated specifically.</LinkTarget>
  <LinkTarget as="li" id="status-trigger-chronological"><StatusTrigger>Chronological</StatusTrigger> — The passage of time triggers the change: a particular date-time boundary is reached.</LinkTarget>
</ul>
</Section>
<Section id="sec-4-4-1-3" title="Status Group Assignment">
<p>In ClickUp's default behavior, status groups propagate down the project hierarchy: a status group set on a
  space is inherited by all folders and lists beneath it, and one set on a folder cascades to every list within.
  This inheritance model treats statuses as a property of the project location—meaning the lifecycle a status
  group models is implicitly scoped to wherever it sits in the project hierarchy.</p>
<p>Our workspace deliberately works against that model. We treat status groups as belonging to task types, not to
  locations. A status group models the lifecycle of a particular kind of entry, so its natural scope is the type
  scope—not the project scope. Since ClickUp does not natively support assigning status groups at the task-type
  level, we enforce this separation through convention: status groups are set exclusively at the list level,
  never on folders or spaces.</p>
<p>To prevent unwanted inheritance, every space and folder (including subfolders) in the workspace uses the
  <StatusGroupLink to="sec-4-4-1-4">Statusless</StatusGroupLink> status group as its default. Lists created
  without a template also receive Statusless by default. A meaningful status group is applied only when a list is
  deliberately configured for a specific task type, ensuring that the status group is always an intentional,
  type-driven choice rather than an inherited artifact of the project hierarchy.</p>
</Section>
<Section id="sec-4-4-1-4" title="Statusless Status Group">
<p>Status is part of ClickUp's base schema and cannot be removed: every entry must have a status. For lists whose
  entries are not meaningfully characterized by a lifecycle—i.e. they have no real status—we assign this status
  group. ClickUp also requires at least one non-closed status and exactly one closed status per status group, so we
  define this minimal, degenerate group with two placeholder statuses:</p>
<ul>
  <li id="status-statusless-none"><Status type="statusless" status="none" showStatusType /> — Represents the absence of a status; entries that "have no status" live here.</li>
  <li id="status-statusless-closed"><Status type="statusless" status="closed" showStatusType /> — Required by ClickUp as the closed status for the status group; unused in practice.</li>
</ul>
<p>All entries on a Statusless list remain in <Status type="statusless" status="none" /> at all times. There are no transitions; no
  status changes are ever made.</p>
</Section>

<Section id="sec-4-4-2" title="Tags">
<p>Tags are a built-in multi-value field used for lightweight categorization. Like a multi-choice Labels field, they let you attach multiple categorical values to an entry, but the main difference is in how they behave in the interface: tags can appear visually next to the entry name, making them useful as immediate, glanceable markers rather than just values stored in a field.</p>
<Section id="sec-4-4-2-1" title="Tag Assignment">
<p>Because ClickUp scopes tags only at the Space level, they are too loosely scoped for broad semantic use across the workspace. To avoid that messiness, we deliberately limit Tags to entries of type <TaskTypeLink to="sec-4-2-1">Task</TaskTypeLink>. This keeps them in a narrow, practical role, while more properly scoped categorization is handled through regular fields such as Labels.</p>
</Section>

<Section id="sec-4-4-3" title="Custom Fields">
<p>Custom fields are the fields we have created and attached to locations or other scopes—not ClickUp's built-in system fields—and they appear in our lists and forms wherever their scope applies. Each custom field is built from one of the <Link to="sec-3-3">field types</Link> that ClickUp offers.</p>
<Section id="sec-4-4-3-1" title="Computational Field Naming">
<p>Computational fields—fields whose values are derived automatically rather than set manually—are prefixed with "=" in their name. This convention makes it immediately clear that such a field should not be edited by hand. It applies to ClickUp's own inherent computational field types like Formula, as well as to auxiliary fields that serve internal processes under the hood and are populated by automations or other logic rather than by direct user input.</p>
</Section>
<Section id="sec-4-4-3-2" title="Hidden Field Naming">
<p>Fields whose names are prefixed with "&" are not meant to be displayed in views. They exist solely for filtering, automation triggers, or under-the-hood calculations. The "&" marker signals that the field is an internal-use artifact—users should never need to see or interact with it directly in list or board columns, and it should be hidden from all standard views.</p>
</Section>

<Section id="sec-4-4-4" title="Templates">
<p>Templates are reusable predefined structures that let us create entries, lists, documents, or other workspace elements in a consistent way without rebuilding them from scratch each time. Their role in the workspace is to turn recurring patterns into repeatable starting points, so that common processes, standard structures, and known best practices can be instantiated quickly and consistently.</p>

<Section id="sec-4-4-7" title="Webhooks & Workers">

<p>Workers are small cloud-hosted processes that run on demand whenever they are triggered. Each worker is responsible for enforcing the operational rules of its respective task type. Workers are triggered by webhooks—HTTP callbacks that ClickUp sends when certain conditions are met.</p>

<p>There are two kinds of webhooks in ClickUp:</p>
<ul>
  <li><strong>Automation webhooks</strong> — Called as an action step within a ClickUp automation. The automation defines a trigger and conditions; when they are satisfied, ClickUp calls the webhook as one of the resulting actions.</li>
  <li><strong>Regular webhooks</strong> — Triggered by global ClickUp events that we subscribe to, independent of any automation. These fire whenever one of the subscribed events occurs anywhere in the workspace.</li>
</ul>

<p><strong>Workers</strong></p>
<ul>
  <LinkTarget as="li" id="worker-task"><strong>Task Worker</strong> — Enforces the <Link to="sec-4-2-1-5">Task Operational Rules</Link> whenever it is activated.</LinkTarget>
