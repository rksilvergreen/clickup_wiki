<p>Project Scope defines the structural layout of the workspace at the location level: its spaces, folders, and lists. This section establishes the general principles and rules that govern how the workspace is organized, addresses common structural dilemmas, and provides a detailed reference of the prominant spaces and their intended purpose.</p>

<Section id="sec-4-3-1" title="Spaces">
<p>The following is a reference of all spaces in the workspace and the role each one serves.</p>

<Section id="sec-4-3-1-1" title="Admin">
<p>An administrative space used for ClickUp workarounds. It is not intended for manual interaction except during maintenance and updates.</p>

<Section id="sec-4-3-1-1-1" title="Intake Folder">
<p>The Intake folder contains one list for each task type: Tasks, Events, Records, and Thoughts. Each list has a ClickUp form attached to it that allows users to quickly add entries of that task type without needing to navigate to the appropriate location in the workspace. The forms serve as a universal capture mechanism—usable from a phone, a browser, or any context where opening ClickUp and navigating to the correct list would be inconvenient or disruptive.</p>

<p>Each form includes a <CustomFieldLink to="space">&Space</CustomFieldLink> field—a <FieldTypeLink to="dropdown">Dropdown</FieldTypeLink> whose options correspond to the main public spaces in the workspace. When a user submits the form and selects a space, the entry is created in the intake list and then automatically moved to the dedicated task-type list within the chosen space. This routing is handled by automations on each intake list that trigger on entry creation and move the entry based on the selected <CustomFieldLink to="space">&Space</CustomFieldLink> value. Because entries are always moved out immediately upon creation, the intake lists themselves remain effectively empty at all times.</p>

<Section id="sec-4-3-1-1-2" title="Automation Folder">
<p>Contains a list for each task type that requires automations. These lists serve two purposes:</p>
<ol>
  <li>They assign automations to a clear task scope: each list is designed to hold every entry of that type across the entire workspace, so automations targeting that type are defined in one place rather than duplicated on every individual list that contains entries of that type.</li>
  <li>They can potentially attach one shared automation set to any scope, or multiple scopes. ClickUp does not let you define automations once and apply them to multiple arbitrary scopes, so the usual workaround is to duplicate the same automations for every list, folder, or space where you want identical behavior. When entries can be represented or routed through these Automations lists, you create, update, and delete automations in one place and they apply across every relevant scope—rather than repeating each change in each scope individually, which is tedious and error prone.</li>
</ol>
<p>To keep these lists complete, each task type that uses a centralized Automations list has a <Link to="sec-4-4-4-1">list template</Link> whose automations add newly created entries to that list.</p>

<Section id="sec-4-3-1-4-1-2-1" title="Feature Request Status Transitions">
<p>Every transition is <strong>manual</strong>. When we align this list with ClickUp&rsquo;s feedback board, a common forward progression is <Status type="feature-request" status="not-submitted" /> → <Status type="feature-request" status="open" /> → <Status type="feature-request" status="future" /> or <Status type="feature-request" status="planned" /> → <Status type="feature-request" status="building-now" /> → <Status type="feature-request" status="beta" /> → <Status type="feature-request" status="complete" />. <em>Future</em> and <em>Planned</em> are different roadmap positions, not a strict sequence—we set whichever matches the post. We may leave an entry in <Status type="feature-request" status="not-submitted" /> until there is a public post to link. An entry may move from any status to any other (for example <Status type="feature-request" status="planned" /> back to <Status type="feature-request" status="open" /> when ClickUp reprioritizes, <Status type="feature-request" status="open" /> to <Status type="feature-request" status="not-submitted" /> when the board post is removed or never existed, or <Status type="feature-request" status="complete" /> to <Status type="feature-request" status="building-now" /> when continued work ships under a follow-up).</p>

<Section id="sec-4-3-2" title="Project Scope Conventions">

<p>This workspace’s location hierarchy supports more than one defensible arrangement for almost any workflow. Unchecked drift—two people solving structurally identical problems with different nests of spaces, folders, and lists—is what conventions are meant to prevent. Rather than prescribing every structural choice upfront, these rules articulate the principles we reuse when partitioning work so placements stay recognizable, navigable, and stable over time.</p>
<p>The following subsections address specific recurring judgments. Taken together they should yield a coherent project scope: one where someone reading the wiki can infer where living work belongs and why, without auditing the entire hierarchy by hand.</p>

<Section id="sec-4-3-2-1" title="Classifying Entries: Lists vs. Views">
<p>Sometimes entries in a list can be classified by a discriminator property—an enum-like characteristic that separates them into distinct types. When this arises, a structural question follows: should the distinction be modeled within a single list or across multiple lists?</p>
<p>The two approaches are:</p>
<ul>
  <li><strong>Single list with a dropdown field and filtered views</strong> — Add a dropdown custom field representing the discriminator, and create a separate view for each value, filtering for entries that carry that value. All entries remain in one list, and the views provide focused perspectives.</li>
  <li><strong>Multiple lists</strong> — Create a dedicated list for each value. If a combined view is needed, it can be constructed at a common ancestor location.</li>
</ul>
<p>The deciding factor is how much value there is in observing all entries together. If entries of different types are frequently viewed, compared, or managed side by side, a single list with a dropdown field and filtered views is preferable—it keeps everything in one place and avoids fragmenting the data. If the types are mostly handled independently, separate lists offer cleaner separation without the overhead of an additional custom field.</p>
</Section>

<Section id="sec-4-3-2-2" title="When to Create a Space">
<p>Not every topic warrants its own space. A topic qualifies for a dedicated space only when all of the following criteria are met:</p>
<ul>
  <li>There is no ambiguity about which list an entry belongs to within the topic.</li>
  <li>No existing space already accommodates the topic (other than General).</li>
  <li>The topic is permanent—it will not end or become obsolete after a finite project concludes.</li>
  <li>The topic requires at least two distinct lists.</li>
</ul>
</Section>
